CLAUSE infrastructure and performance audit, October 18, 2026

Historical audit recorded before the implementation. For the current architecture and verification commands, see [INFRA.md](../INFRA.md). Current measurements and rollout gates are recorded in [the performance report](../bench/performance/results/2026-10-18/REPORT.md). File line references below describe the audited snapshot.
===========================================================

The current Fastify, Node, Postgres, Vite and React stack is a reasonable base. The largest visible costs come from request sequencing, repeated whole-document transfers, serial database writes and browser layout. Changing frameworks would leave these costs in place.

This audits the current working tree, including the recent uncommitted hardening changes. It does not establish that those changes are deployed. Vercel dashboard settings, database region, compute sizing, production query plans and production traffic were not inspected. Authentication and tenancy remain outside this audit's implementation scope. No application code was changed during this audit.

The orientation history utility was unavailable at both installed fallback paths. The audit therefore uses the current code, Git state, the session's implementation history, existing benchmark artifacts and new local smoke measurements.

Measured locally during this audit
---------------------------------

The existing disposable SQLite load tool was run with `pnpm load 1 1 --warmup=0` and `pnpm load 8 3 --warmup=1`. Node was 26.7.0, while the project targets Node 24. Each document was approximately 0.96 MB, below the 1 MiB inline threshold. The load client and server shared this machine. These short runs establish symptoms, not statistical capacity estimates or hosted performance.

| Scenario | One client p95 | Eight clients p95 | Eight clients throughput | Repo target |
|---|---:|---:|---:|---:|
| Read an inline document | 4.3 ms | 12 ms | 859 requests/s | 50 ms |
| Word search | 2.4 ms | 186 ms | 74 requests/s | 300 ms |
| Exact search | 5.2 ms | 443 ms | 32 requests/s | 300 ms |
| One replacement per client's own document | 65 ms | 859 ms | 18 requests/s | 500 ms |

No HTTP errors occurred. The concurrency difference combines increased contention with an increase from one to eight documents. The scenarios are separate loads; they do not represent a mixed production workload. Postgres and Blob performance remain unmeasured in this audit.

Findings in implementation order
--------------------------------

1. **P1: Remove history verification and migration from request startup.** [config.ts](/Users/term_/Desktop/Sandstone/apps/api/src/config.ts:43) calls `backfillLargeContent()` whenever a Postgres store initializes with Blob configured. [The backfill](/Users/term_/Desktop/Sandstone/apps/api/src/store/postgres.ts:592) processes missing references and then downloads and hashes every referenced revision, sequentially. This repeats even when the migration is complete. Every fresh instance can therefore perform work proportional to the entire revision history before its first database operation completes. For illustration, 1,000 revisions at 25 MiB would require about 24.4 GiB of verification reads per instance; that is arithmetic, not an observed corpus. Run migrations and backfill as explicit resumable jobs. Verify each object before committing its reference, store the verification outcome, and run later integrity sweeps separately. Startup should check a schema/version marker and connect. A missing migration should produce a bounded readiness failure rather than silently starting a bulk job.

2. **P1: Batch chunk writes and stop replacing every index row for a small edit.** [commitRevision](/Users/term_/Desktop/Sandstone/apps/api/src/store/postgres.ts:354) locks the current document through its CAS update, deletes all chunks, then awaits an individual INSERT for each 8,000-code-unit chunk. A 25 MiB ASCII document produces 3,277 chunks. At an illustrative 1 ms database round trip, just those serial inserts imply roughly 3.3 seconds, before other work. Use parameterized `INSERT ... SELECT FROM unnest(...)` in bounded batches with the existing `pg` driver. Benchmark `COPY FROM STDIN` through `pg-copy-streams` for large ingestion. Preserve the CAS and transaction. A later step should give paragraph chunks stable identities and update only changed chunks. Do not issue thousands of concurrent queries against the same transaction connection.

3. **P1: Make metadata reads independent of document size.** [getDocument](/Users/term_/Desktop/Sandstone/apps/api/src/store/postgres.ts:330) selects `content`; [document GET](/Users/term_/Desktop/Sandstone/apps/api/src/routes/documents.ts:95) loads it before checking the ETag; the content-URL endpoint does the same before signing a Blob reference. Consequently, even a 304 or a metadata response can pull 25 MiB from Postgres into Node. Add a metadata/reference store method with persisted byte length and UTF-16 length. Fetch content only for operations that consume it. After a verified migration and recovery rehearsal, large historical snapshots can use Blob as their body store instead of retaining full revision bodies in Postgres. Current code stores a full body in current documents, revisions, chunks and Blob. That is about four logical copies before indexes, WAL and old tuples; actual disk use depends on compression and content.

4. **P1: Remove the large-read waterfall and pin content to its version.** [resolveDoc and resolveReceipt](/Users/term_/Desktop/Sandstone/apps/web/src/lib/api.ts:118) fetch metadata, then another API endpoint for a download URL, then the Blob. The first two API requests both load document content today. The intermediate URL also names the current document, so a concurrent edit can make a v1 metadata response download v2 text. Return a signed URL or a reference pinned to the exact immutable revision in the initial response. Validate the returned version/hash before associating downloaded text with editor state. Cancel obsolete downloads on navigation. Add a byte-bounded cache keyed by document and immutable version; signed-URL expiry and content-version expiry are different concerns.

5. **P1: Bound search work before transferring bodies.** [Word search](/Users/term_/Desktop/Sandstone/apps/api/src/store/postgres.ts:382) counts and ranks with correlated chunk queries, then fetches full bodies for the result page. Ten maximum-sized documents could transfer 250 MiB internally to produce small snippets. [Exact search](/Users/term_/Desktop/Sandstone/apps/api/src/search.ts:69) fetches every candidate body, scans all occurrences, sorts all documents and only then paginates. Make the database return matching chunk windows, versioned offsets and bounded context. Use indexed title search instead of computing a title vector per row for each query. Inspect actual `EXPLAIN (ANALYZE, BUFFERS)` plans and `pg_stat_statements` before choosing a query rewrite. Exact occurrence ranking needs a deliberate contract: use maintained counts, a bounded ranking process, or change the ranking semantics explicitly. Simply adding LIMIT before the current application sort would change results.

6. **P1: Preserve search semantics while fixing chunking.** [chunkText](/Users/term_/Desktop/Sandstone/apps/api/src/store/postgres.ts:195) slices fixed UTF-16 intervals. A full-text query is tested against a single chunk, so terms in separate chunks cannot jointly satisfy the document-level AND query; phrases or words split at a boundary can also be missed. A surrogate pair can be cut between chunks. Migration offsets use Postgres character counts while new JavaScript chunks use UTF-16 offsets. Use paragraph-aware boundaries with safe splitting and explicit offset units, document-level term combination and sufficient overlap for supported phrase queries. Test cross-boundary words, distant terms, phrases and non-BMP characters before replacing full-body reads.

7. **P1: Bound browser layout and computation for large contracts.** [DocPane](/Users/term_/Desktop/Sandstone/apps/web/src/components/DocPane.tsx:35) renders the entire body into the DOM. A small number of spans still leaves the browser laying out all text. [Workspace state](/Users/term_/Desktop/Sandstone/apps/web/src/lib/workspace.tsx:445) reconstructs the proposed full text on the main thread. Virtualize measured paragraph blocks and maintain a separate logical selection model that supports selections crossing unmounted paragraphs, keyboard selection, copy, search navigation and accessibility. Move expensive text transforms to one persistent Web Worker. Send the body once, then edit operations and version tags, rather than cloning 25 MiB for every interaction. For a future editable text surface, benchmark CodeMirror's viewport against custom virtualization before choosing it.

8. **P2: Isolate expensive export/import work.** Word export computes a redline and builds the DOCX in the request process. Large diffs, packaging and parsing can compete with lightweight requests on a shared Node event loop. Put large exports, imports, integrity checks and bulk AI reviews behind durable jobs with cancellation, resource limits, idempotency and retries. Return a job handle, then an immutable Blob download. On Vercel, evaluate Workflow SDK first; for a dedicated worker beside Postgres, evaluate pg-boss. Use Piscina only inside a process with an appropriate CPU and memory allocation. A thread pool does not add CPU capacity to an undersized function.

9. **P2: Confirm placement and pool budgets.** [vercel.json](/Users/term_/Desktop/Sandstone/vercel.json) contains no region pin; dashboard configuration may still supply one. Confirm API and database placement before changing drivers. The application already uses `attachDatabasePool`, so that recommendation is already satisfied. The pool defaults to three connections per instance and lacks an explicit connection timeout. Measure acquisition time, `waitingCount`, query execution and lock wait separately. Size total connection capacity across maximum instances, and set bounded connection/statement deadlines appropriate to each operation. Benchmark Neon HTTP for isolated metadata reads only; preserve an interactive transaction driver for CAS writes and locking. A driver change does not fix thousands of serial statements.

10. **P2: Use immutable Blob caching deliberately.** [content-storage.ts](/Users/term_/Desktop/Sandstone/apps/api/src/content-storage.ts:61) sets `useCache: false` on object reads and signed downloads. Immutable, unique object paths are compatible with caching once their upload is verified. Use consistent origin reads where required for first-write verification, then benchmark cached immutable downloads. Preserve signed access, expiry and private browser caching policy. Do not put private content into a shared public response cache.

11. **P2: Make performance observable across the actual bottlenecks.** [telemetry.ts](/Users/term_/Desktop/Sandstone/apps/api/src/telemetry.ts:15) creates a periodic metrics exporter but retains no provider handle for flush/shutdown, so request completion or instance suspension can occur before export. Add a bounded export lifecycle suitable for Vercel and verify delivery through a real collector. Store-method duration does not separate pool queueing, network time, index work and CPU. Add sampled stage measurements, event-loop delay, memory, Blob transfer time and bytes, query counts per edit, AI latency/error/cancellation and browser LCP/INP/CLS. Keep labels bounded and exclude document text and identifiers.

Packages worth using
--------------------

These are choices based on the reviewed code and official project documentation, not a claim that a package version alone improves latency. No packages were installed for this audit. Pin compatible stable versions only after checking Node 24 support, peer dependencies, release age, licensing and the resulting lockfile.

| Choice | Decision for CLAUSE | Purpose and source |
|---|---|---|
| `fastify`, `pg`, `@vercel/blob`, Vite, React | Keep | Existing foundation is suitable. Fix the work performed on each request first. |
| Existing `pg` plus parameterized bulk SQL | First database optimization | Batch normal chunk writes without introducing another database abstraction. [Postgres bulk-loading guidance](https://www.postgresql.org/docs/current/populate.html) |
| `pg-copy-streams` | Benchmark for bulk ingestion | Stream `COPY FROM STDIN` through the existing transaction client. [Maintainer repository](https://github.com/brianc/node-pg-copy-streams) |
| `@tanstack/react-virtual` | First browser prototype | Virtualize measured paragraph blocks while retaining the document's visual presentation. Selection and accessibility need explicit design. [Official introduction](https://tanstack.com/virtual/latest/docs/introduction) |
| `comlink` with native Web Workers | Use if profiling confirms text-processing long tasks | Run document operations outside the main thread. The worker should retain versioned state to avoid full-string copying for each operation. [Maintainer repository](https://github.com/GoogleChromeLabs/comlink) |
| `workflow` | Preferred Vercel job candidate | Durable orchestration for exports, imports and backfill; heavy CPU still needs properly sized execution steps. [Vercel Workflow](https://vercel.com/workflows) |
| `pg-boss` | Alternative to Workflow on a persistent worker | Reuse Postgres for a modest durable job workload; isolate job load and connection use from interactive traffic. Do not install both queues by default. [Maintainer repository](https://github.com/timgit/pg-boss) |
| `piscina` | Conditional dedicated-worker addition | Bounded Node worker threads for CPU work, with task and memory limits. [Maintainer documentation](https://github.com/piscinajs/piscina) |
| `@codemirror/state`, `@codemirror/view` | Alternative editor prototype | Built-in viewport rendering and incremental document state if CLAUSE becomes a full text editor. Do not add alongside a custom editor without a clear reason. [CodeMirror viewport guide](https://codemirror.net/docs/guide/#viewport) |
| `@neondatabase/serverless` | Measure as a read-path experiment | Neon recommends HTTP for single queries/non-interactive transactions; interactive transactions require its session-capable interface or the existing TCP `pg` pool. [Official driver docs](https://neon.com/docs/serverless/serverless-driver) |
| `web-vitals`; k6 CLI | Measurement additions | Real-user browser metrics and production-shaped load scenarios with automated thresholds. [Web Vitals](https://web.dev/articles/vitals), [k6 testing guide](https://grafana.com/docs/k6/latest/testing-guides/automated-performance-testing/) |

Redis, a new ORM, Elasticsearch, a different frontend framework and a runtime rewrite are not the first changes justified by this evidence. A shared cache becomes useful when traces show repeat work across instances. A separate search service becomes useful when Postgres query plans and measured corpus scale justify its operating cost. React Query can help request caching, but it does not solve document layout or version races on its own.

Recommended delivery sequence and acceptance
--------------------------------------------

1. Move migrations/backfill out of request startup; introduce metadata-only reads; pin content URLs to immutable versions. New-instance readiness should require bounded DB setup, not a scan of history. A 304 should transfer no body from Postgres, and metadata query bytes should remain approximately constant across document sizes.
2. Bulk chunk writes while preserving CAS, then update only changed chunks. Track query count and locked transaction duration. A maximum-sized create should use a bounded number of statements, not 3,277 insert round trips. Cover conflicts, rollback and search-boundary semantics.
3. Return bounded search windows before transfer, then virtualize the browser and cancel obsolete downloads. Trace bytes between Postgres and API, and between API and browser. Measure cross-block selection and scroll behavior with actual 25 MiB documents on constrained mobile hardware.
4. Move large CPU operations to jobs; complete metric export lifecycle and sampled stage measurements. Verify a large export cannot monopolize unrelated metadata/read requests.
5. Run isolated Postgres/Blob scenarios at 1, 10 and 25 MiB with 1, 8 and 32 concurrent clients. Include cold and warm instances, same-document contention and separate-document writes, small and whole-document edits, realistic text, repeated boilerplate and Unicode. Use a separate load-generator machine, the deployed Node 24 runtime, repeated runs and a mixed traffic scenario. Verify actual content bytes and hashes, not just a successful metadata response.

Suggested product targets, not measured claims: metadata p95 below 100 ms when warm; search p95 below 300 ms on the agreed corpus; browser INP at or below 200 ms at the 75th percentile; ordinary small edits on 1 MiB documents p95 below 500 ms at eight clients. Establish a separate 25 MiB commit budget after bulk writes and hosted measurements. Avoid promising the 1 MiB latency target for 25 MiB whole-document rewrites without evidence.
