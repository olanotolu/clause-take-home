# CLAUSE walkthrough narration

Synthetic ElevenLabs narration. Fictional contract data.

Hey guys, I’m Ola. I built Clause for Sandstone. Let’s jump in.

Here’s the workspace. I can see what’s waiting on legal, open a request, and get to the document from one place.

This card is our request. Acme wants a one year disclosure term, while keeping the exceptions and five year survival period. We also need to update the governing law. I’ve put the outcome beside the document so I can keep checking what we’re trying to achieve.

I’ll open the agreement from the request. The board gives the work some context, but the heart of the assessment is right here: edit document text and search its content. Let’s start by finding the clause we actually need to change.

I’m searching for the two year disclosure term. The result gives me the matching passage and the document version. When I open it, Clause selects that exact text. I don’t have to hunt through the agreement or guess which occurrence the result meant.

Now I’ll replace two years with one year. I’m staging the edit first, so the saved document hasn’t changed. The engine checks that this target exists and identifies one place. If the wording repeats, I need context or an occurrence number to make it precise.

Here’s the redline. Red is what I’m removing, and green is what I’m adding. We’re still on version one. Every edit in a batch refers to that same original text, so an earlier replacement can’t move a later target. If one edit is invalid, none of the batch saves.

Now, Clause CI is a check against requirements I’ve saved for this document. Here I want to keep the disclosure exception, retain the five year survival language, and avoid a perpetual term. These are exact text checks, so they don’t need a model call.

Let me deliberately make a bad change. I’m staging removal of the disclosure exception. The sentence is there, so the edit itself is possible. But it’s language we said we wanted to keep. Nothing has been saved yet, and that’s the important part.

When I run the check, you can see the exception requirement fail against the proposed text. The other rules still hold. This is why I separate finding the right text from checking the result. An edit can be precise and still break the thing I wanted to preserve.

I’ll discard that mistaken removal and check again. Now the one year change is still staged, and the protected language stays intact. Exact checks are repeatable checks on text. When I ask a model to judge meaning, I treat its answer as advice that can be wrong.

That looks right, so I’ll apply it. We now have version two. The saved text, search index, and history update together. I still decide whether the legal request is complete. Applying an edit doesn’t automatically mean the business outcome has been met.

Next, I’ll use the assistant for the governing law change. I’m asking for Delaware to become New York while keeping those exceptions and the survival period. It’s the same fictional agreement, and I’m asking for a proposal I can inspect.

This part uses a real model request. The model suggests edits; it can’t save them directly. The usual editing engine checks the targets afterward. I’ve bounded the request to twenty five seconds and limited the output. An oversized replacement gets rejected rather than cut off.

Here’s the proposal, its explanation, and the version it was checked against. I can review it before I apply anything. Semantic checks also verify quoted evidence, but a real quote can still be used to support a wrong claim. I don’t treat that as legal approval.

There’s also an optional experimental judge called Jev. My existing account returned an access error, so it’s disabled here. I haven’t measured its accuracy. The separate language model citation experiment includes false support cases, which is a useful reminder of the limits.

I’m happy with this proposed change, so I’ll apply it and create version three. The server checks the version again at save time. If someone else got there first, my stale edit would be rejected. It won’t silently overwrite their newer work.

In Activity, I can see the revisions and the changes behind them. Restoring makes another version instead of erasing history. The Word export includes tracked changes. I tested accepting and rejecting those with independent readers; I’m not claiming every Word version was checked.

Let’s search for the language I just saved. It’s available straight away. The server returns a consistent search snapshot, and the browser checks the loaded version and passage. If a hit is stale, it asks me to search again. It also protects any edits I already have staged.

I’ve also added source-backed templates. The details show the source, version, license, and attribution. Common Paper provenance follows a document created from a template. The curated form stays read only, while the new copy is editable. It’s a starting point that still needs review.

These integrations are a demo with sample files. They show how browsing and importing a document would feel. They aren’t live customer repository connections. Real connections need the provider credentials and workspace admin setup, and I’ve kept that distinction visible.

On mobile, search gets the full screen. That gives the passage and results room to breathe instead of squeezing them into a desktop dialog. The browser journeys cover mobile and desktop, including exact selection, protected drafts, and older responses arriving after a later navigation.

Let me show you the API behind that edit. I send JSON with the version I expect, the text I’m targeting, and its replacement. The response gives me updated text and a change receipt. This calls the same editing service the screen uses.

And here’s a real stale version response: a conflict. I asked to edit version one, but the document was already on version three. The current text stays safe. Ambiguous targets and overlapping changes fail too. Offset edits must include the text expected at that position.

The stack is fairly direct. React handles the interface. Fastify validates requests. A pure TypeScript engine resolves the changes. The database commits only if the version still matches. SQLite runs locally, and Neon Postgres runs the hosted app. Their indexes serve search.

This release passed three hundred and seventy seven SQLite tests, three hundred and eighty three Postgres tests, and eighteen browser journeys. The database suites overlap. CI also checks types, lint, coverage, and builds.

I reran the same large document benchmark around the search change. Local SQLite searched a ten mebibyte file in about twenty one milliseconds for a rare word and twenty five for a common phrase. Hosted Postgres is capped at five hundred thousand characters.

The engine is only part of the cost. Indexes, revision snapshots, and returning the full document take more work. Full snapshots simplify restoring, but use more storage. I’d optimize from these measurements rather than assume the engine is the bottleneck.

Here’s what I’d add for production: authentication, document permissions, and tenant isolation. I’d move larger snapshots into object storage and use paragraph chunks for search. Durable workers would handle large imports and AI jobs. This is a design proposal, not infrastructure I’ve already deployed.

I’d monitor latency by document size, conflicts, search delay, queue age, and model spend. I’d test restoring backups and rolling back releases. Workspace budgets need durable enforcement. More services should earn their place through measurements.

A few limits to be clear about. The public demo is shared, so it’s for fictional data, not confidential contracts. Editing is plain text, semantic review is advisory, and the real connectors need setup. I also went beyond the suggested time box while expanding the product.

That’s Clause: precise edits, searchable content, and a reviewable history. The repo has setup steps, sample requests, tests, measurements, and the one page infrastructure proposal. You can try the live demo too. Thanks for taking a look. I’m happy to walk through the code and the trade-offs with you.
